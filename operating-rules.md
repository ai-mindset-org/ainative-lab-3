# Operating Rules – правила личного harness

> AIN3 · AI-Native Sprint III. Свод правил, по которым реально работает система автора лабы: два волта, ~200 скиллов, мульти-агентные сессии Claude Code / Codex, наблюдаемость сессий. Каждое правило родилось из инцидента или из третьего повторения, поэтому у большинства есть строка «почему».

---

## 0. Рамка

Harness – система договорённостей, которые направляют модель в нужное русло и оставляют проверяемый след. Шесть рабочих зон: **context · memory · guardrail · review · naming · communication**. Правила ниже разложены по этим зонам.

## 1. Context – что агент знает до задачи

1.1. **Router читается до первой задачи.** В корне рабочей папки лежит `AGENTS.md` (или `CLAUDE.md`): кто оператор, какой процесс, правила имён, карта папок, что нельзя. До 40 строк для одного процесса.

1.2. **Router – индекс, а не склад.** Глобальный router держится «худым» (~200 строк): правила-указатели, детали вынесены в отдельные reference-файлы, которые агент читает по требованию. Почему: всё, что лежит в router, загружается в каждую сессию и стоит внимания модели; разбухший конфиг деградирует работу тише, чем ломает.

1.3. **Source map: 3–5 источников, не больше.** Каждый источник – три поля: `source · why · access boundary`. Контекст – маленький необходимый кусочек, а не весь корпус (формула M1).

1.4. **Контекст собирается компилятором, не свалкой:** raw sources → отбор → normalized context pack (goal · current state · rules · examples · boundary). Пять полей переносят задачу между сессиями и между людьми.

## 2. Memory – что переживает сессию

2.1. **Один факт = один файл.** Память – каталог маленьких markdown-файлов с frontmatter (тип: user / feedback / project / reference) плюс индекс `MEMORY.md` ≤200 строк. Почему: файл легко исправить, удалить, проверить; монолитная память копит противоречия незаметно.

2.2. **Файловая память – Pareto-оптимум старта.** Бенчмарк LoCoMo: файловая память 74.0%, специализированная графовая 68.5%. Апгрейд до графа/индекса нужен после ~30 конфликтующих фактов, не раньше.

2.3. **Brief, not reload.** Перед закрытием сессии – handoff 5–7 строк: что сделано, где лежит, следующий шаг, открытые решения. Свежая сессия с коротким брифом обыгрывает полную перезагрузку истории уже после 1–2 циклов: старые логи топят внимание модели.

2.4. **Транскрипты append-only.** Сырые источники не редактируются; выводы живут в отдельных `{analysis}`-файлах со ссылками на сырьё.

## 3. Guardrail – границы

3.1. **Три контура хранения:** public (можно наружу) · team (внутренний рабочий) · local (не покидает машину). Каждый файл рождается в своём контуре; перенос между контурами – осознанное действие с санитизацией.

3.2. **Ask-first список.** Агент останавливается и спрашивает перед: публикацией наружу, удалением, действиями с деньгами, изменением доступов, сообщениями людям от имени оператора. Список живёт в router.

3.3. **Registry прежде governance.** Невидимыми агентами нельзя управлять: любой повторяющийся агент/крон попадает в реестр – identity · owner · scope · last run · stop control.

3.4. **У агента есть паспорт.** Owner, scope, permissions, expiry, kill switch. Ответственность не переходит к агенту ни в какой точке маршрута.

3.5. **Секреты не живут в файлах контекста.** Токены – в keychain/env; в волте и репозиториях их нет. Проверка перед каждым push.

## 4. Review – проверяемый след

4.1. **Eval-футер в каждом ответе агента:** `T:✓ R:✓ C:○` – text (структура/ясность/действие), rules (имена/границы/тон), code (работает/минимально/идиоматично). Бинарно, без градаций. Три фейла в одной зоне подряд – повод для нового правила.

4.2. **Evidence log – append-only журнал прогонов:** дата · что запущено · output (адрес файла) · gap · одна правка системы. Первый прогон – диагностика, а не финал: его задача проявить слабую зону.

4.3. **Одна правка за цикл.** После review система получает ровно одно изменение (источник, правило или шаг скилла). Почему: множественные правки не дают понять, что сработало.

4.4. **Скилл рождается из третьего повторения.** SkillsBench: рукописные скиллы из своей практики дают +16.2 п.п. качества, самосгенерированные пачкой – около нуля. Формат: папка + `SKILL.md` (trigger · steps 4–8 · output · evidence).

## 5. Naming – адресация

5.1. Полная конвенция – [naming-convention.md](naming-convention.md). Ядро: `{project} {type} description – YYYY-MM-DD.ext`, дата в конце, en-dash, имя латиницей.

5.2. **Форматы по роли памяти:** `.md` договорённости · `.jsonl` события · `.parquet` аналитика · `.sqlite` runtime-состояние.

5.3. **Новые папки не создаются походя.** Смысл живёт в имени файла; папка добавляется решением, а не рефлексом.

## 6. Communication – люди и агенты в одном контуре

6.1. **Роутинг по стоимости:** поиск/сканирование – дешёвой модели, реализация – средней, синтез/архитектура – дорогой. Суб-агент без явного выбора модели наследует дорогую – главная утечка бюджета.

6.2. **Две среды – один контракт.** Claude Code и Codex читают зеркальные router-файлы; передача между ними – файлом-хендоффом, а не памятью платформы. Сессии разных агентов над одним репо делят полосы: один пишет файл – второй туда не пишет, координация через bridge-файл.

6.3. **Наблюдаемость сессий.** Инспектор сессий отвечает на «кто что менял и когда»: timeline, файлы, суб-агенты, граф связей. Неделя автора в цифрах (07–14.07.2026): 8 сессий · ~434 часа агентской работы · 6.5M токенов на выходе · 28 суб-агентов · 9 коммитов · 4 деплоя – у каждого шага есть след.

6.4. **Refresh ritual.** Раз в 1–2 недели: сверить router с реальностью, выкинуть мёртвые правила, обновить source map, прогнать один эталонный прогон. Система без ухода дрейфует за 2–3 недели.

## 7. Лестница масштаба

```
голова → файл → индекс → git → сервис → автономия
```

Перелом personal → team везде один – git: история, ревью, общий адрес. Personal OS (один владелец, локальный контекст, первый скилл) → Team OS (общий репозиторий, библиотека процессов, ритм ревью) → Company OS (операционная модель, управляемая память, портфель evidence). Неделя W1 – ступени 1–2, и это осознанный выбор, а не компромисс.
